# Intersection-counter session handoff — 2026-05-20

## Where we are

Worked the turn-accuracy problem end-to-end against a real manual TMC
count for Sunnyvale TX (project `97a7849a`, intersection 1, camera 1).
**The classifier rewrite from the 05-18 handoff was working in the
wrong direction** (the 57% turn fraction it produced was inflated by
short-stub trajectories that should have been filtered as
insufficient_data). Today's fixes brought turn fraction to a realistic
33% — but ground truth comparison revealed two deeper bugs that are
parked for the next session, where overnight Balanced runs are
feasible.

## What was fixed (and is committed)

| Change | Why |
|---|---|
| `TRAJECTORY_MIN_POINTS` 2 → 5, `TRAJECTORY_MIN_DISTANCE_PX` 8 → 50 | Old floor let 2-pt 9-px "trajectories" reach destination scoring; softmax invented confident wrong answers. 26 of 45 baseline throughs were these stubs. |
| `score_destination_leg` exit-displacement gate (20 px) | Refuse to assign a destination when the tail window has near-zero motion. Returns `None`, pipeline downgrades to insufficient_data. |
| Removed d845a4a "last-chance origin assignment" in `_finalize_vehicle_data` | Per-frame loop already attempts assignment; finalize-time retry was only rescuing the stubs the floor now rejects. |
| Per-mode tracker thresholds (`tracker_match_threshold`, `tracker_activation_threshold` in `PROCESSING_MODES`) | Fast mode at `detection_skip=3` has a Kalman-frame-rate mismatch (ByteTrack assumes consecutive `update()` calls are 1 frame apart). Loosened Fast to match=0.95 / activation=0.15. Accurate/Balanced stay at strict defaults. |
| New "Balanced" mode: yolo26s @ 960, detection_skip=1 | Hits ~6× slower than real-time on this hardware (i5-1135G7 CPU, no CUDA). Avoids Fast's Kalman mismatch entirely. Best ratio of accuracy to runtime for full-day clips. **Set as the recommended mode for production counts.** |
| `TRIPWIRE_HALF_LENGTH_PX = 120` (up from hardcoded 40 in `tripwire_from_point`) | Edge-leg origins (L19 at `(85, 370)` in Sunnyvale) had vehicles entering past the short tripwire. **Not validated yet** — same-session A/B comparison wasn't feasible at Balanced's rate; needs overnight rerun. |

Tests: 458 passing in `backend/tests/`. The five pre-existing sklearn
failures (`No module named 'sklearn.cluster'`) and two OneDrive
teardown errors are unchanged from before — not introduced by today's
work.

## Parked bugs (the next session's targets)

### Bug A — L19 catastrophic origin miss (highest single recall lift)

L19's synthesized tripwire sits at `(85, 370)` — the lower-left edge of
the 640×480 frame. NB Belt Line is by far the dominant approach (536
vehicles in 23 min), but YOLO doesn't detect those vehicles until
they're well inside the FOV, past the tripwire. They miss the
synthesized line entirely; the heading-fallback then mis-assigns them
to L18 (the opposite end of the same road), L20, or L21 — or drops
them as insufficient_data.

**Tried but unvalidated:** Extended `TRIPWIRE_HALF_LENGTH_PX` from 40
→ 120. Same-session A/B was impractical (each Balanced run takes
~2 hours real-time to produce a meaningful sample). The change is
committed but its effect needs an overnight comparison run.

**Other approaches to try:**
- Anchor tripwires to the frame boundary when the origin point is
  within K pixels of the edge (so vehicles entering from the edge
  *must* cross some part of the line).
- Replace tripwires with first-detection-zone clustering at
  calibration time — collect K trajectory starts per leg, learn the
  zone shape, classify new vehicles' first detection position against
  it. Bigger change but more robust to camera-perspective
  irregularities.

### Bug B — `derive_movement` doesn't fit skewed intersections

Two pieces of evidence from ground truth:

- L18 has 67 phantom lefts; manual count says L18 has **zero** left
  turns at this intersection. Rank-based `derive_movement` calls L18→L20
  a "left" even though L20 (delta 31° CCW from L18) isn't a left turn
  geometrically — it's a slight bend in the road.
- L21 (Northwest Dr) has 41 "throughs"; manual says **zero**.
  Northwest Dr is a side street that *terminates* at the intersection.
  There is no physical through movement from L21. Rank-based logic
  calls L21→L20 a "through" because L20 sits opposite in CCW rank
  order — but they're not paired roads.

The rank-based derive_movement I added in the 05-18 classifier rewrite
was correct for orthogonal 4-way intersections. It's wrong here
because:
- Belt Line at this intersection has Driveway (L20) on one side as a
  road-continuation candidate, and Northwest Dr (L21) on the other —
  but Northwest Dr **isn't** a through road.
- The legs aren't symmetric around Belt Line's axis.

**Approaches to try:**
- Capture a "through-pair" hint per leg at calibration time
  (engineer selects "this leg pairs with leg X for through traffic"
  or marks the leg as terminating).
- Detect terminating side streets geometrically: legs whose
  reference_heading isn't roughly opposite (within e.g. 60°) any other
  leg's reference_heading are terminators — no through movement
  possible from them.
- Surface the OD matrix alongside the TMC table in the UI so engineers
  can spot these failures themselves without a manual count.

## How to use what we built

### Iterating on accuracy with the harness

```bash
# 1. Make a code change
# 2. Hard-restart the server (uvicorn reload doesn't fully cycle the
#    pipeline thread — see existing memory). Kill the python process
#    listening on :5000, then `py start_server.py`.
# 3. In the UI: Sunnyvale TX project -> Processing tab -> Balanced mode
#    -> Restart from beginning -> Confirm & process. View live for
#    qualitative check on the new behavior.
# 4. Cancel after meaningful sample accumulates (60+ events).
# 5. Compare to baseline:
py scripts/groundtruth.py --diff baseline
# 6. If recall improved on the metric you care about, save a new
#    named snapshot:
py scripts/groundtruth.py --save tripwire-fix-attempt-1
```

### Visualization helpers

```bash
# Plot all events colored by movement (great for spotting short stubs):
py scripts/debug_turn_viz.py
# -> screenshots/turn_debug_sunnyvale.png

# Plot trajectory starts colored by origin leg (great for diagnosing
# origin attribution like Bug A):
py scripts/debug_origin_viz.py
# -> screenshots/origin_attribution_sunnyvale.png
```

Both scripts are hardcoded to project `97a7849a` camera 1 for now.
Easy to generalize when we tackle the second intersection.

### Overnight Balanced run

Balanced on the full Sunnyvale clip is roughly 6× slower than
real-time on the user's CPU. AM peak (7-9 AM) + PM peak (4-6 PM) = 4
hours of footage = ~24 hours processing. Start it at the end of a
workday, check in the morning.

## Important quirks / state to know

- **Mode toggle is on Setup → Processing tab only.** Once processing
  starts you land on the live dashboard which doesn't surface the
  current mode. The dashboard could use a small read-only "Mode: X"
  badge — low-priority UX fix.
- **Uvicorn reload still doesn't fully cycle the live pipeline.**
  After editing backend Python, hard-restart the server. Kill the
  Python process via PowerShell's `Stop-Process` (PID from netstat
  may be stale; the actual process might be a multiprocessing child).
  Confirmed today: kill the multiprocessing child PID even after
  taskkill says "not found".
- **23 min of footage took ~2 hours of Balanced processing today.**
  Originally I underestimated by 10×; iterations at Balanced speed
  must be planned around overnight runs.
- **The user has manual ground truth for this exact clip.** That's
  rare and valuable. Wherever possible, validate accuracy changes
  against `scripts/groundtruth.py` rather than visual intuition —
  the visual gestalt of "tracks look good" was misleading us.
- **The user's mental model:** still "the trajectories are obvious to
  the human eye — let the data tell us." For Bug A and B both, a
  data-driven clustering tier remains the bigger-but-right answer.
