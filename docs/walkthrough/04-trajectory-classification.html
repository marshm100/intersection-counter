4. Trajectory Classification

With origin assigned, what movement did the vehicle make? The answer is derived from the trajectory's shape and the intersection geometry — no hardcoded turn matrix, no exit zones. Two stages: a quality gate, then a destination-leg score.

Stage A — insufficient_data quality gate

Filter out trajectories that don't carry enough motion to classify reliably. A 2-point, 9-px "trajectory" used to reach scoring and the softmax would invent a confident wrong answer. 

num_points        < TRAJECTORY_MIN_POINTS (5)        → insufficient_data
total path dist   < TRAJECTORY_MIN_DISTANCE_PX (50)  → insufficient_data

Plus a tail-window check inside the destination scorer: if the last 20% of the trajectory moved less than EXIT_DISPLACEMENT_MIN_PX (20), scoring refuses to assign a destination (vehicle stalled or trajectory finalized mid-frame).

Stage B — destination-leg scoring

For each leg (including the origin, so u-turns are detectable), compute an "expected exit direction" — the unit vector from the intersection center to that leg's origin point. Score the trajectory's exit velocity and exit position from center against this expected direction. 

for leg in all_legs:
    expected_dir   = unit(leg.origin - intersection_center)
    heading_score  = dot(exit_velocity,         expected_dir)
    position_score = dot(exit_pos_from_center,  expected_dir)
    raw_score[leg] = 0.7 * heading_score + 0.3 * position_score

# Convert to probability via tempered softmax (temp=4 sharpens the peak)
posterior = softmax(raw_score, temperature=4.0)
destination_leg = argmax(posterior)

The dot products are in [−1, 1]. Temperature 4 makes the argmax usually exceed 0.5 when one leg is clearly favored, without being so peaky that small geometric differences get drowned out.

From (origin, destination) to movement label

Once origin and destination legs are picked, the movement label (through / left / right / u_turn) is derived from their reference-heading geometry by derive_movement.

Same leg = u-turn. Otherwise, the non-origin legs are sorted by counter-clockwise delta from the origin, and the rank tells the label:

Other-leg countRank 0Rank 1Rank 2
3 (canonical 4-leg)leftthroughright
2 (T-junction)leg within 60° of opposite = through; else both turns
1 (degenerate)left if delta < 180°, else right
4+ (5-way)nearest-canonical (90/180/270)

Why we don't use fixed angle buckets

A naive rule like "delta ≤ 45° = through, 45-135 = turn, ≥135 = u-turn" works for orthogonal intersections. Sunnyvale's legs sit at 259° / 61° / 291° / 123° — nowhere near 90° apart. Using fixed buckets here labels real destinations wrong: 

origin = L18 (ref 259°)
→ L20 (ref 291°), delta = 31°  → bucket rule says "u_turn"  (wrong!)
→ L21 (ref 123°), delta = 224° → bucket rule says "through" (wrong!)

The rank-based approach gets these right because it adapts to whatever geometry exists.

Bug B — when even the rank approach is wrong

The rank logic still assumes the four legs are peer roads. At Sunnyvale:
  • L18 has 67 phantom lefts in the baseline data. Manual count: zero left turns from L18. Rank labels L18→L20 a "left" even though L20 is a slight bend in the road, not a left-turn road.
  • L21 has 41 fake throughs. Northwest Dr (L21) is a side street that terminates at this intersection — there is no physical through movement. Rank labels L21→L20 a "through" because L20 sits in the rank-2 position, but they're not paired roads.
Parked for next session. Approaches to try (in increasing order of effort):
• Detect terminating side streets geometrically: legs with no near-180° pair = no through possible from them.
• Capture a "through-pair" hint per leg at calibration time.
• Surface the OD (origin-destination) matrix in the UI so engineers can audit it themselves.

Worked example: L19 right-turner

Suppose a vehicle entered via L19 (heading 61° on approach) and exited toward L21 (a slight bend roughly to the east-southeast). Origin = L19, destination = L21.

Origin ref61°
Destination ref (L21)123.1°
Delta CCW from origin(123.1 − 61) mod 360 = 62.1°
Sorted other-legs by delta L21 (62.1°), L18 (198.3°), L20 (229.8°)
L21 is rank 0 of 3 →left

Whether "L19 → L21" is really a left turn at this intersection is debatable — that's the data-driven question Bug B exists to answer.

  ...timestamps + class + bbox dims

The classifier_* columns are diagnostic — they let us audit a misclassification after the fact without re-running detection. That's what made the offline replay in scripts/replay_origin.py possible.
