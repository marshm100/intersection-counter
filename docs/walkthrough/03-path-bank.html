3. The Path Bank

The single most important object in the current pipeline. A per-camera set of polylines — one per real turning movement — that captures the actual shape of every road through the intersection. Origin, destination, and movement are all read off the path a vehicle matches, not guessed from a point and an angle.

Why a single origin point isn't enough

Calibration (page 1) captures one click per leg plus a heading. That was the whole geometry in the v2 pipeline, and it has a structural flaw at these cameras: vehicles enter YOLO's field of view already mid-turn. A track's first few points reflect where it is in the turn, not which approach it came from — so the entry tangent points the wrong way, and a point-and-heading scheme mis-attributes it. Queuing, occlusion, and edge-of-frame entry make it worse.

The fix is to match against the whole road, not a point. If we know the shape of "EB Barnes Bridge → NB Belt Line (a right turn)" as a curve in image space, a vehicle that traces that curve is that movement — regardless of where in the curve YOLO first caught it. The bank is that library of road shapes.

What a path is

One row in the intersection_paths table (mirrored on disk as evaluations/recal_cam<N>.json). Each path is a single origin→destination movement with the polyline that vehicles making it actually follow: 

{
  "origin_leg_id":      38,            # EB Barnes Bridge Rd
  "destination_leg_id": 39,            # NB N Belt Line Rd
  "movement_label":     "right",
  "polyline": [[633,252],[610,244],[586,234],[546,222],   # image-space curve,
               [540,205],[560,196],[575,192],[581,189]],  # entry → through → exit
  "supporting_count":   43,            # how many real tracks fit it when built
  "source": "data-driven-heading-recovered"
}

A four-leg intersection has up to 12 turning movements (each of 4 legs → the other 3); a real one has fewer, because not every movement physically exists. The bank holds only the movements Miovision confirms occur — typically 6–10 paths per camera.

How the bank is derived

The bank is not hand-drawn. scripts/build_bank.py derives it from real tracks, gated by ground-truth volumes. Turn geometry comes from the video; which turns are real comes from Miovision — neither is ever guessed.

1 Track the calibration window — run BoT-SORT over the detection cache (page 2) for a representative window. Each surviving track is a point list.
2 Read the real movements from Miovision — the per-minute origin→destination matrix says which (origin_leg, dest_leg, movement) cells occur and at what volume. Cells below min_support are skipped.
3 Group tracks into cells — primary binning is by the nearest leg origin-anchor to each track's start and end. (Where that drops a real movement, a heading-based recovery re-bins by direction of travel — see page 7.)
4 Fit one mean polyline per cell — average the grouped tracks into a single smooth curve of ~15 points.
5 Quality-gate it — reject paths that would misbehave at attribution time (below).

The quality gates

A fitted polyline can be geometrically wrong in ways that cause it to steal traffic at attribution time — a "snap-magnet." The gates are all data-driven (no per-camera flags):

GateRejectsWhy
magnet a TURN path that is geometrically straight (chord/arc > 0.95) and over-supported (support > 3× its Miovision volume) a straight "turn" is really an arterial through mislabeled by endpoint grouping; at apply it captures the through stream
over-collection a heading-recovered cell whose support exceeds 3× its Miovision volume looser heading binning can sweep in unrelated tracks on dense cameras
straight-recovery a recovered TURN that is straight (chord/arc > 0.95), regardless of support a recovered turn that doesn't curve is arterial throughs in disguise — real turns curve (a genuine recovered right turn measures ~0.43)

These exist because the bank is built from tracker output, so it inherits the tracker's mistakes. The whole story of catching and gating those mistakes — including the per-camera A/B discipline that is the final gate — lives on page 7.

What the bank then drives

Once built, the bank is the geometry every downstream stage reads from:

  • Origin & attribution (page 4) — each live trajectory is matched against the bank's sub-curves; origin is read off the winning path.
  • Movement classification (page 5) — the matched path already carries its movement_label and destination leg.
Apply it safely. Writing a bank into project.db goes through scripts/apply_bank.py / apply_hybrid.py, which back up first. A direct PUT /calibration/legs is destructive — it wipes the camera's events — so bank changes never go through that path.
