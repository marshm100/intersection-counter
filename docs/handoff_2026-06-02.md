## #1 NEXT TASK — fix the BoT+bank "snap-magnet" (rare-turn paths steal throughs)
**Symptom:** BoT+bank gross DEGRADES as the window grows — cam4 18.5% (5min) → 66.7% (30min);
cam5 37% → 98.7%; cam3 13.2% → 18.3%. The bytetrack-HYBRID instead IMPROVES with more data
(cam4 43→33, cam5 69→43).
**Root cause (diagnosed read-only):** a LOW-SUPPORT RARE-TURN bank path becomes a "snap magnet"
that captures the dominant THROUGH tracks. Concrete: cam4 @30min had EB-left manual=6 but **ours=325**,
while NB-thru collapsed 728→349. At 5-min that rare turn is below `min_support=5`, so the bad path
never exists; at 30-min it clears the gate and corrupts throughs. (Same family as cam1's old "phantom
snap to mis-placed L24".)
**Why hybrid is immune:** it keeps bytetrack throughs and only uses BoT for turns, so no turn path can
steal a through. That's why it won at 30-min and is what cam4/cam5 shipped on.
**Fix ideas (pick by measurement):**
- Raise/relativize `min_support` in `scripts/build_bank.py` (e.g. support must be ≥ K AND ≥ a fraction
  of the cell's manual volume), so noisy rare-turn paths don't get created.
- Path-shape quality gate: reject bank polylines that are too straight / too short to be a real turn
  (a turn path that looks like a through is the magnet).
- In the matcher/retrack snapping, protect throughs: don't let a turn path capture a track whose
  endpoints are a clean origin→opposite-leg through. (Look at where `apply_bank.py`→`hybrid_prototype.retrack`
  assigns movement/dest from the bank.)
**Validate:** rebuild banks + re-measure cam3/cam4/cam5 at BOTH 5-min and 30-min with
`od_accuracy --camera N`. Goal: BoT+bank should no longer degrade with window length. If fixed, cam3
may beat its 5-min bank and cam4/cam5 may beat the hybrid → re-apply winners (atomic backup).

## The toolchain (all camera-parameterized)
- **Metric:** `py scripts/od_accuracy.py --camera N [--db <db>] [--start-hms 07:00:00 --minutes M] [--show-od]`
  — per-minute OD error vs the camera's Miovision XML. Universal; replaced the old measure_cam2.
- **Leg↔approach map:** `od_accuracy.leg_idx(N)` joins `legs.cardinal_direction` (N/S/E/W) to the
  XML approach-name cardinal prefix (NB/SB/EB/WB). Data-driven; works for T's (3 legs) and 4-ways.
- **Bank:** `py scripts/build_bank.py --camera N [--minutes M] [--out f.json] [--min-support K]`
  → `evaluations/recal_camN.json` (raw-track polylines + Miovision OD).
- **Apply (two candidates — ALWAYS measure both, ship the winner):**
  - `py scripts/apply_bank.py --camera N [--apply]` — BoT-retrack-with-bank (throughs AND turns via bank).
  - `py scripts/apply_hybrid.py --camera N [--apply]` — bytetrack throughs + BoT merged turns + bank.
  - Both make an atomic backup on `--apply`.
- **Cache build:** `py scripts/reprocess_camera.py --camera N --mode balanced --start-hms 07:00:00
  --minutes M --yes` — DEVICE=openvino (Intel iGPU) by DEFAULT, ~7 fps (3× CPU). DESTRUCTIVE
  (deletes+regens that camera's events). Add `--cache-only` for a NON-DESTRUCTIVE cache rebuild on a
  SHIPPED camera (events go to a throwaway temp DB; project.db untouched).

## Gotchas / how we work here
- Diagnostic-first, data-driven, robust (no band-aids). Engineer visual gate before any production
  apply; atomic backup before mutating project.db. Metric = per-minute GROSS.
- **Pick the throughs tracker per camera BY MEASUREMENT** — it flips: cam2/cam4/cam5 → hybrid; cam3 →
  bank (cam3's bytetrack had 61 phantom T-stem "throughs"). Never assume.
- Do NOT ship the 30-min PREVIEW banks (`recal_cam{2,3}_30min.json`) as-is — they exhibit the
  snap-magnet bug. The cam2 30-min "preview" 87.5% is bank-ONLY (not cam2's hybrid path) — ignore it.
- `reprocess_camera.py --yes` is DESTRUCTIVE; use `--cache-only` to touch a shipped camera's cache
  safely. OneDrive holds file locks (scratch DBs live in the system temp dir to dodge this).
